A chat agent for mission planning

Let an operator describe a mission change in plain language, inspect a deterministic preview, and choose whether to apply it. The map and editor remain the source of truth.

Planning only

Keep the mission in the editor

Recommended default, subject to the privacy decision. Run the tool loop on the app server over a temporary snapshot. Coordinates would reach that server for geometry calculations, but stay out of model context. Choose browser tools if coordinates must stay on the device.

The proposed app adds a chat panel beside the map. The implemented Node runtime exposes four fixed tools: get_mission_context, preview_change, propose_change and ask_clarification. It accepts a caller-owned snapshot and preview operations. The browser UI, HTTP route, provider connection, persistence and mission acceptance flow remain proposed. The shared evaluator remains an integration dependency for the unfinished editor.

Scope boundary. DJI Fly remains where the operator starts and supervises a flight. This proposal adds no aircraft control, live telemetry, autonomous takeoff or flight-file compatibility claims. A valid geometry result is not operational flight clearance.

Current baseline

Planner contract exists

src/index.ts exports planMission(input: unknown) and domain types. src/core.ts validates route or orbit inputs with Zod, calculates WGS84 geometry and returns calculated waypoints or invalid-input issues. Public types are deeply readonly.

Inputs cover shot, height above takeoff and framing. Speed, capture actions, review flags and conversation state are outside the current planner contract.

Experience and interaction

The map, forms and chat refer to one mission revision. A context chip above the composer identifies the selected target or route, revision and height datum. The user can attach a selected map object to a message to avoid ambiguous location descriptions.

When the agent proposes an edit

  1. Clarify missing intentThe user asks for a wider orbit. Since no radius was specified, the agent asks. A question ends the run; human response time does not hold a server function open.
  2. Preview against the snapshotThe user replies '45m'. The agent calls preview_change with radiusM=45, reads the result and calls propose_change with that preview ID.
  3. Show a temporary path and change cardThe UI shows the candidate path and '30m to 45m'. Only Apply changes commits one revision and clears prior review.
  4. Keep follow-up explicitReject leaves the draft unchanged. 'Actually, make it 35m' starts a new run against the current revision. Typing 'yes' can continue discussion, but only the explicit proposal action applies an edit in the first version.

Keep control and recovery visible

Show short tool activity, tool results and the final explanation. Do not expose private model reasoning. The user can Stop, Retry or start a New conversation. Manual editing remains available during failures.

On mobile, chat and map can use separate views of the same draft. A preview is labelled temporary and cannot change the accepted draft before the user applies it.

New conversation clears dialogue while keeping the mission. Retrying is explicit and uses a new request ID and fresh snapshot.

Architecture and ownership

The proposed app keeps the accepted draft in the browser. A future server route would authenticate and bound each run. The implemented runtime accepts caller-supplied context and preview operations, then stages a proposal for the caller. Browser recomputation and user acceptance remain future integration work.

trusted app and domain operationsbounded request and tool looptemporary run state

Browser owns

Live draft, revision, local persistence, review and acceptance. Chat owns messages and pending proposal cards, never waypoints or review flags. A future transport adapter can map runtime results and activity to app events.

Server owns

A thin Next.js Node route handles authentication, request parsing and response streaming. A small agent module prepares context, runs the bounded tool loop and contains provider-specific formats.

Domain owns

The shared mission evaluator and its browser integration remain proposed. The runtime receives a caller-owned preview operation. Acceptance remains a future browser mission operation.

Operational store owns

Atomic quota counters, expiring concurrency leases and run deduplication IDs. This is not a mission database. A verified server-side subject selects counters. For an owner-only deployment, a verified session may map to one fixed owner budget.

Request flow

  1. Capture one immutable turnThe browser sends the snapshot, selected object IDs, current revision, user message and a bounded window of recent chat.
  2. Protect the routePOST /api/chat authenticates the caller, validates the request and reserves a turn budget before provider work begins.
  3. Prepare model contextThe server uses allowlisted metadata. Raw coordinates stay in the server snapshot and outside model context.
  4. Validate every tool callThe dispatcher validates complete arguments, resolves object IDs against the snapshot and invokes application code.
  5. Evaluate a candidatepreview_change invokes the shared pure evaluator, including planMission. Compact results return to the model; the loop may repeat within its budget.
  6. End with a proposal or answerpropose_change packages a previously evaluated candidate. The server streams a completed proposal event and ends the run. A clarification ends the run without a proposal.
  7. Recheck in the browserThe browser recomputes the preview. Apply changes checks current identity and validity, then makes one atomic mission edit.
  8. Keep review and export separateA proposal cannot grant review, approve flight export or change compatibility status.

A snapshot is read-only evidence for one run. Hypothetical candidates live in a per-run map keyed by previewId. Each preview replaces allowed fields relative to the base snapshot; it does not implicitly build on another preview. propose_change can reference only a valid preview from that run. Select one final proposal per turn.

Runtime tools and proposed app interfaces

The four tool names below are implemented. Their mission descriptions and preview operations come from the caller. The broader app interfaces and edit rules still need to align with Stage 2.

get_mission_context()

Inspect relevant state

Reads selected object roles, editable parameters and missing fields. It cannot enumerate unrelated missions or retrieve raw coordinates for the model.

preview_change(change)

Evaluate one candidate

Accepts a strict semantic change, resolves existing IDs, creates an isolated candidate and runs the shared evaluator. Returns preview ID, validity, changed fields, bounded diagnostics and supported measurements. Missing or unsupported data is explicit.

propose_change(previewId)

Return a review card

Returns the evaluated change and base identity to the UI. Unknown or invalid previews fail. Prefer local recomputation and transmit the semantic change, not coordinates, to the browser.

ask_clarification(question)

Request missing input

Ends the run with an explicit question of at most 1,000 characters. The UI can distinguish clarification from an answer without guessing from prose. Proposal and clarification tools must each be the only call in their batch.

Supported changes

Limit the first tool to orbit and route geometry, height above takeoff and framing supported by the mission domain. Do not expose a generic JSON patch. Weather, terrain, imagery, geocoding and external document retrieval need separate evidence and privacy designs.

Use a discriminated union. For example, updateOrbit takes an existing orbit ID and explicitly present radius, direction or arc fields; setHeight takes heightAboveTakeoffM; setFraming uses a supported choice and selected target ID.

Creation and batches

createOrbit and createRoute require existing map object IDs and all mandatory geometry values. An ordered atomic batch may combine height and radius edits. Keep a small operation cap and reject duplicate writes to one field.

Derive tool schema and TypeScript types from one source. Network and model input are parsed at the boundary; shared pure domain operations own meaning and acceptance.

Proposed state shapes

SnapshotIdentity = { missionBranchId, revision, inputDigest, schemaVersion, plannerVersion }

ChatTurn = { conversationId, requestId, base: SnapshotIdentity, snapshot, selectedIds, message, recentHistory }

Proposal = { proposalId, runId, base: SnapshotIdentity, change, previewSummary }

RunEvent = started | textDelta | toolStarted | toolFinished | proposal | completed | failed

RunOutcome = answered | needsInput | proposed | cancelled | stale | failed | budgetExceeded

ProposalStatus = pending | applied | rejected | stale

Three app-owned operations hide the implementation
  • runTurn(turn, signal) returns an asynchronous stream of app events and hides provider formats, dispatch, budgets and stream handling.
  • previewChange(snapshot, change) hides field resolution, hypothetical edits and planning. It returns incomplete, invalid or valid with an evaluated candidate.
  • acceptProposal(proposal, expectedIdentity) obtains the current draft and atomically compares identity, validates and commits. It returns applied, alreadyApplied, stale or invalid.

The UI does not coordinate these domain rules.

Trust, context and privacy

Use current state as authority

Current structured mission state outranks conversational recollection. Include a small recent history window, never an unbounded transcript. In long chats, ask the user to restate omitted intent in the first version. Later summaries are narrative context and cannot override current state or restore approval.

New conversation clears dialogue while keeping the mission.

Minimise provider data

Coordinates go transiently to the app server for deterministic evaluation. Do not persist snapshots, log raw prompts or enable SDK payload tracing by default. Exclude coordinates, map pixels and full geometry from provider prompts, tool outputs and errors.

User text and object labels may still contain location information and reach the provider. This is data minimisation, not a guarantee that no location reaches the model. Provider retention and model choice remain release decisions.

Protect the boundary

Use authenticated access, same-origin checks where cookie sessions apply, payload caps and a fixed tool allowlist. Origin checks alone do not authenticate a caller. Reconstruct trusted instructions on the server.

Treat labels, history and returned browser data as untrusted text. Reject client-supplied system messages, tool definitions and claimed prior approvals. Validate complete tool arguments before execution.

Keep capabilities narrow

There is no shell, arbitrary URL fetch, code execution, raw coordinate creation or flight-control tool. Render assistant text safely without raw HTML.

Application labels distinguish geometry validity from site, terrain and flight checks that do not exist.

Local conversation history

Save messages, compact tool summaries and proposal status per mission branch in IndexedDB. Do not save private model reasoning or provider-internal messages. Keep chat out of shared planning exports by default.

Restored proposals remain historical and need regeneration before applying. Reload ends an active run, and clearing browser storage removes local history. Cross-device history is deferred.

Correctness when state changes

Bind each proposal to branch ID, revision, canonical input digest, planner version and schema version. The digest covers every evaluation input, including selections, limits and settings when supported. It detects mismatch; it does not prove independent review.

Apply as one domain operation

Keep a proposal ID ledger within the mission branch so repeated Apply is idempotent. The domain atomically compares identity, validates the edit, commits one revision and invalidates review.

Browser acceptance reruns the shared evaluator. Require matching planner and schema versions. Deployment skew produces a refresh-required result. A successful preview cannot bypass missing settings or broader review gates.

Make late events harmless

A manual edit or a change to any bound selection or evaluation input during a run marks it stale and aborts it. Harmless map highlighting does not. Late events cannot change the draft or reactivate a proposal. A cancelled run has a terminal ID that the browser ignores even if the provider finishes.

Closing or reloading the tab ends the run in Stage 3. Model failure preserves chat and the last accepted draft. Retry is explicit, uses a new request ID and snapshot, and never starts another paid run automatically when a request is replayed.

Operational limits

The implemented runtime caps each turn at 4 model calls, 6 tool calls and 30 seconds, and disables SDK retries. One active run per owner remains a proposed application policy; the runtime does not enforce it. These are application limits, not provider or Vercel limits.

Budget and concurrency

Reserve quota before the first provider call, count actual calls and tokens, and release the concurrency lease on every exit. Lease expiry handles process crashes. Disable SDK retries if defaults would add calls.

Use atomic counters, expiring leases and run deduplication IDs. Fail closed if quota storage is unavailable.

Bound every payload

Retain the README's 64KB incoming body cap and 4,000-character user-message cap. Bound snapshot size, selected objects, chat history, tool output and total streamed output. Reject oversize input rather than truncating required mission fields.

Set provider-specific token and per-call output caps after model selection. If authoritative state cannot fit, return a clear context-too-large result. Bound preview work too.

Measure spending honestly

Replace the README's 100 single-call interpretations per day with a configurable daily token or spend budget plus a request-rate cap. Reserve a conservative maximum turn allowance atomically, then reconcile actual use.

If usage is unknown after a timeout, keep the reservation instead of refunding speculatively. Proposal application can be idempotent through a proposal ID ledger. Provider billing still cannot be guaranteed exactly once after an ambiguous disconnect.

Log run facts, not mission content

Record run ID, outcome, model and prompt version, latency, tool names, token use and error category. Exclude mission content. Verify authenticated protection for the API and every deployment before release.

Alternatives considered

The recommendation keeps the mission local while limiting the agent loop to one server request. The right choice changes if coordinates must stay on the device or the product needs recovery across devices.

Decision status. Option B is the proposed independent server-snapshot design. Its use depends on the product owner accepting transient coordinate processing by the app server; that is a proposed default, not settled approval. Option A remains the browser-tools fallback if that data flow is unacceptable. The cross-judge review also preferred B.

A · Browser tool execution

Coordinates stay on the device and the local planner runs every preview. The server streams tool calls to the browser and resumes after results return.

This adds network round trips, continuation validation and failure states. Budgets must span continuations, and browser results remain untrusted reports.

Choose when coordinates must never reach the app server.

Recommended

B · Ephemeral server loop

The browser owns the mission. The server evaluates hypothetical edits in one bounded request with the same planner. No durable mission database is needed.

The costs are transient location disclosure to the app server, version checks and no recovery after closing the tab.

Choose for Stage 3 if transient coordinate processing by the app server is accepted.

C · Server-owned mission service

Store missions, conversations and runs with authorisation and optimistic revision checks. Durable workers can resume runs and support multiple devices or collaborators.

This adds synchronisation, retention, migrations and offline complexity.

Choose when cross-device recovery or collaboration is a real requirement.

Why not only a one-shot interpreter?

A structured single call is cheaper and easier to bound. It cannot inspect tool results and revise its approach within a turn, so it does not fully meet the requested agent experience. Keep it as an optional simpler mode if measured cost or latency later warrants it.

Why one agent?

One agent is enough for the initial tool set. Multiple specialist agents add coordination and conflicting proposals without a demonstrated need. A workflow framework earns its place when durable long-running jobs, branching workflows or many integrations arrive.

SDK, model and build sequence

SDK and model choice

The implemented Node-only runtime uses AI SDK generateText for bounded multi-step tool calls. It is exported as @drone/mission-planner/agent and accepts an ordinary SDK LanguageModel at the composition boundary. It does not configure a provider or implement chat transport, streaming UI or an HTTP route.

The package pins AI SDK 7.0.138. Each turn allows at most 4 model calls, 6 tool calls and 30 seconds. SDK retries are disabled. The runtime passed 59 tests with a scripted model and the actual planner, plus typecheck, lint and build. A live model is not yet connected. History, model output, answer text and structured tool results have fixed size limits. The caller supplies the immutable snapshot, schema, redacted context function and preview operation. The caller must redact coordinates and other private data from context, summaries and diagnostics. The runtime keeps the exact validated change and opaque candidate outside model messages, and returns a proposal without accepting it. Live provider connection, HTTP authentication, durable quotas, chat UI and mission acceptance remain proposed.

Evaluate one model first

Choose one tool-capable model using a small fixed evaluation set. Compare a capable low-latency model with a stronger model on clarification, schema adherence, tool choice and refusal to invent missing geometry.

Choose using observed correctness, latency and cost per completed turn. Do not add automatic routing or provider fallback before those measurements. A provider change stays within an adapter, but model behaviour still needs evaluation.

Decisions to revisit

Is transient coordinate processing by the app server acceptable?

Default to yes for this proposal. Choose browser-side tool execution if the answer is no.

Should every mission change require Apply?

Default to yes. Reversible automatic draft edits could be a later preference; review remains explicit.

Should chat survive across devices?

Default to local history for Stage 3.

Which mission types should the agent handle?

Default to supported orbit and route geometry. Add speed, capture actions and multiple shots when the mission domain supports them.

Which provider, retention policy and daily spend cap fit?

Defer final values to implementation evaluation and account setup.
